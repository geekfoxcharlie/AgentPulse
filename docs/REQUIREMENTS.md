# AgentPulse 产品需求

状态：当前产品基线

## 1. 产品定义

AgentPulse 是一套运行在本机、供人和本地 Agent 共同查阅的 API 能力目录。

它集中登记已经由人工申请和配置好的第三方 API，使不同 Agent、不同工具和不同项目能够复用同一份接口知识，不必重复寻找密钥、猜测环境变量名或重新研究调用方式。

AgentPulse 是动态说明书，不是 API 网关。Agent 在查阅后自行选择接口，并直接向第三方服务发出业务请求。

## 2. 要解决的问题

本地同时使用多个 Agent 和多个项目时，API 配置会逐渐分散，产生以下问题：

- 不清楚本机已经配置了哪些 API。
- 不记得密钥存放位置和环境变量名。
- 不记得认证参数应放在 Header、Query、SDK 还是其他位置。
- 不清楚某个 API 当前是否能够完成最小请求。
- 不同 Agent 会重复研究同一个 API 的用法。
- Agent 无法自行申请 API Key，需要复用人已经完成的配置工作。

## 3. 目标用户与场景

主要用户是同时使用多个本地 Agent、开发工具和项目的个人开发者。

典型场景是：Agent 准备执行搜索或其他外部能力任务时，先查询 AgentPulse 中对应能力组，查看已配置接口及其即时健康状态，再自行决定使用哪个接口并直接调用。

## 4. 产品原则

### 4.1 Agent 自主决策

AgentPulse MUST 提供事实和调用说明，但 MUST NOT 代替 Agent 选择、排序或路由第三方 API。

### 4.2 直接调用

Agent MUST 直接调用第三方 API。AgentPulse MUST NOT 作为业务请求代理，也不负责在请求路径中注入密钥。

### 4.3 本机信任

AgentPulse MUST 假设在同一操作系统用户下运行的本地 Agent 是可信调用方。

系统的目标是管理密钥的可发现性，而不是阻止本地 Agent 读取密钥。AgentPulse 不提供进程隔离、密钥防读取或恶意 Agent 防护。

### 4.4 单一事实来源

每类信息 MUST 只有一个维护位置。界面、README 和迭代 Spec 可以引用事实来源，但 MUST NOT 维护第二份同类事实。

## 5. 功能需求

### R1：API 能力目录

系统 MUST 登记所有可供 Agent 使用的 API，并至少记录：

- 稳定且唯一的 API ID；
- 名称、描述和所属能力组；
- 服务地址和官方文档地址；
- 是否启用；
- 认证引用；
- Agent 可执行的调用说明；
- 最小健康检查定义。

系统 MUST 支持用能力组组织 API，例如 `search`。能力组名称不是健康检查结果，也不代表系统推荐顺序。

### R1.1：内置独立搜索目录

内置模板是可安装的公开定义，不是已配置 API。当前 `search` 内置目录仅包含以下独立搜索 API：

- Exa Search；
- Firecrawl Search；
- Tavily Search；
- X API Search Posts；
- Serper Google Search；
- Brave Search。

这里的“独立”是指 Agent 可以直接向服务的数据 API 发送请求并获得机器可读搜索结果；目录 MUST NOT 把必须经由语言模型调用的服务端搜索工具作为独立搜索 API 模板提供。

该目录是经过人工研究后维护的候选集合，不构成运行时的质量排名或自动路由规则。Brave Search 保留为独立索引选项，但本机 Agent 在依赖它前 SHOULD 先查询其缓存健康状态。用户或可信 Agent 仍可以通过 CLI 登记其他 API；它们不因此成为内置推荐目录的一部分。

### R2：凭据元信息

AgentPulse MUST 记录凭据的环境变量名、配置位置和请求注入方式，但 MUST NOT 把真实密钥值作为 API 配置的一部分保存。

配置位置可以是 `.zshenv`、由 `.zshenv` 加载的专用文件或其他本地位置。系统 MUST 如实记录实际位置，不强制所有凭据采用同一种存储方式。

AgentPulse 的查询结果和 Web 页面 MUST 默认不输出环境变量的真实值。Agent 可以根据变量名和位置自行读取凭据并完成直接调用。

### R3：Agent 查询入口

CLI MUST 是 Agent 使用 AgentPulse 的正式查询入口，并同时提供：

- 适合人阅读的默认输出；
- 结构稳定、适合 Agent 解析的 JSON 输出；
- 能力组列表查询；
- 单个能力组及组内 API 查询；
- 单个 API 的完整调用说明查询。

AgentPulse 第一阶段 MUST NOT 把正式 HTTP API 或 MCP 作为必要产品接口。

### R4：按组健康检查

Agent MUST 能在查询能力组时请求健康状态。发生该查询时，系统 MUST：

1. 检查该能力组的缓存结果；
2. 在缓存有效时直接返回结果；
3. 在缓存不存在或过期时，对组内所有已启用 API 执行各自定义的最小测试；
4. 保存并返回本次检查结果。

健康缓存的默认 TTL MUST 为一小时。API 配置或相关凭据引用发生变化时，对应缓存 MUST 立即失效。

最小探测 MUST 尊重供应商的计费模型与最低请求限制。对于按返回资源计费的 API，探测定义 MUST 使用满足接口约束的最小结果数，并在调用说明中提示成本边界。

健康状态至少 MUST 区分：

- `healthy`：最小请求成功；
- `unhealthy`：请求已执行但失败；
- `misconfigured`：配置不完整或所需凭据不可用；
- `disabled`：被人工停用且未参与检查；
- `unknown`：尚未产生检查结果。

每条结果 MUST 包含检查时间、缓存过期时间和不泄露密钥的简化错误信息。延迟可以展示，但不作为质量评分。

### R5：不统计真实成功率

AgentPulse MUST NOT 根据最小健康检查推断真实业务成功率，也不在第一阶段采集 Agent 的真实调用结果。

系统 MUST NOT 提供历史成功率、自动推荐、自动降级或服务质量排名。

### R6：通过 Agent 配置

API 与能力组的新增、修改、启用和停用 MUST 通过 CLI 完成，预期操作者是本地 Agent。

配置流程 MUST 支持 Agent 收集必要信息、生成结构化配置、执行校验并触发首次健康检查。写入前 MUST 校验配置，不能要求 Agent 直接修改内部数据库。

实际密钥可以由可信 Agent 或用户写入所登记的位置；AgentPulse 只维护其名称、位置和用法，并验证引用是否可用。

### R7：只读 Web 页面

AgentPulse MUST 提供仅在本机访问的 Web 页面，用于展示：

- 能力组及 API 列表；
- 配置完整性；
- 环境变量名和配置位置；
- 调用说明；
- 最近一次健康状态及缓存时间。

Web 页面 MUST NOT 提供新增、编辑、删除、启用、停用或密钥输入能力。第一阶段的页面浏览和刷新 MUST NOT 自动触发第三方 API 健康检查。

### R8：上下文引导

系统 MUST 提供一段可注入不同 Agent 上下文的简短引导，告知 AgentPulse 的存在，并建议 Agent 在使用外部 API 前先通过 CLI 查询相关能力组。

该引导 MUST 只承担发现和入口说明，不应把完整 API 清单复制进 Agent 上下文。

## 6. 非功能需求

- AgentPulse MUST 默认只服务当前本机用户。
- Web 服务 MUST 默认只监听回环地址，不能默认暴露到局域网或公网。
- 配置和健康状态 MUST 跨项目共享，不能绑定到某一个业务项目目录。
- 配置错误 MUST 指向具体 API、字段或凭据引用。
- 日志、错误和健康结果 MUST 避免输出真实密钥。
- CLI JSON 输出 MUST 具有明确版本，以支持不同 Agent 稳定解析。
- 系统 MUST 能在没有常驻后台服务时完成 CLI 查询和健康检查。

## 7. 明确非目标

第一阶段不包含：

- 代理、转发或拦截 Agent 的业务 API 请求；
- 阻止本地 Agent 读取环境变量或密钥文件；
- 自动申请、购买或轮换 API Key；
- 根据健康状态替 Agent 选择接口；
- 收集真实调用遥测或计算成功率；
- 正式 REST API、远程访问或多用户服务；
- Web 配置后台；
- 强制所有 Agent 使用 AgentPulse；
- 跨设备同步或云端托管。

## 8. 成功标准

产品达到最小可用状态时：

1. 用户可以登记多个能力组和 API，并知道每个凭据的名称与位置。
2. 任意能够执行本地命令的 Agent 可以获得结构化 API 清单和调用说明。
3. Agent 可以按组取得一小时内复用的最小健康检查结果。
4. 用户可以通过只读 Web 页面查看相同配置和已有健康状态。
5. AgentPulse 不进入第三方 API 的业务请求链路。
